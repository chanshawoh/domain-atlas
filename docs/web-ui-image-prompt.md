# DomainAtlas 完整工作台 UI 生图提示词

用途：生成首版 Web UI 的视觉参考图。下面代码块可以整体复制给生图工具。画面内数据均为明确标注的示例，不代表当前仓库统计。本文件只提供提示词，未调用生图服务。

```text
请设计并生成一张 DomainAtlas 的高保真桌面 Web 应用完整界面图。输出单张、正面、平面的应用截图，画面从顶部导航到内容底部完整可见。逻辑画布 1600×1000，建议输出 3200×2000 的清晰图像，保持 8:5 比例。只生成一个真实可落地的页面，不要多屏拼贴、透视样机、浏览器外框或设计说明展板。

【产品是什么】
产品名：DomainAtlas。
产品定位：面向 AI 辅助开发的本地业务地图与变更记录工具。
核心价值：让每次 AI 开发，都留下可追溯的业务变化。
用户通过“业务域 → 业务能力”理解项目，从关联变更追溯需求、实际文件变化、证据与 Git 提交状态。
这是日常使用的专业工作台，不是品牌官网。界面以简体中文为主，产品名、文件路径、分支名保留英文。

【要呈现的这一刻】
用户正在查看示例项目“Commerce · 商城服务”的业务地图，关注“订单与售后”域中的“退款审批”能力，并选中了最近一条“新增退款审批”变更。中央地图、下方变更列表、右侧详情应通过一致的蓝色选中态产生视觉关联。
在顶部项目名称旁清楚显示小标签“示例数据”。所有业务名称和数字都是设计演示数据。

【整体视觉】
采用精致、克制、信息清楚的现代开发工具视觉语言：Swiss grid、清晰的字体层级、适度紧凑的信息密度、稳定的面板结构。可以参考 Linear 的文字密度与 GitHub 的证据阅读体验，但不要复制它们的品牌或 Logo。
整体为浅色主题。页面背景 #F6F7F9，主要面板 #FFFFFF，左侧栏 #F1F3F6，分隔线 #E2E6EC。主文字 #182230，辅助文字 #596579，选中态和主要操作 #2563EB，浅蓝底 #EFF6FF。
绿色只表达“已提交”等明确状态，琥珀色表达“待提交”或“低置信度”；每个状态都有清楚文字，不仅靠颜色。未采集测试用中性灰色。
面板圆角 10px，按钮圆角 6px，细边框，阴影极轻。使用 8px 间距体系。正文逻辑字号 14px，辅助文字 12px，页标题 24px；中文采用思源黑体或 Noto Sans SC 风格，英文采用 Inter 风格，文件路径采用 JetBrains Mono 风格。
图标统一为 18px 的细线图标。使用简单的节点连接图形作为 DomainAtlas 标识，不使用 emoji。

【空间布局】
顶部栏高 56px，横贯整张页面。
顶部以下，左侧导航宽 200px，中央工作区宽约 1040px，右侧固定详情面板宽 360px。中央内边距 24px，主要区块间距 16px。
右侧详情是并排的固定阅读面板，不遮盖地图，不出现蒙层。
中央从上到下依次是：标题及检索栏、紧凑摘要条、业务地图面板、最近变更面板。所有主要区域在当前画布内合理容纳。

【顶部项目栏】
左边显示节点状标识和 DomainAtlas 字标。
中央偏左显示“Commerce / 商城服务”和小标签“示例数据”。
右边显示细线分支图标与“main”，以及一个低调的“本地项目”标签。
不要显示团队头像、账单入口或未经证明的“实时在线”状态。

【左侧导航】
导航项只有三个：“业务地图”“变更记录”“接入说明”。
“业务地图”处于选中状态，浅蓝背景，蓝色图标和文字，其他项目用深灰文字。
底部显示小字“本地事实存储”和路径“.domainatlas/”，风格安静，不放大型宣传文案。

【中央标题与摘要】
标题“业务地图”。副标题“从业务能力追溯每一次变化”。
标题右侧有一个搜索输入框，占位文字“搜索业务域或能力”，旁边是小型“刷新”图标按钮。
下方是同一个横向容器内的四组紧凑摘要，用细竖线隔开，不做四张巨大的仪表盘卡片：
“业务域 3”
“业务能力 7”
“变更记录 24”，辅助小字“已提交 20”
“待提交 4”
数字大小适中，不出现增长率、折线趋势、进度百分比或质量评分。

【业务地图：核心视觉区域】
地图占中央最重要的面积，高约 350px。白色面板中使用极淡的点阵底纹。
面板顶部左侧文字“业务结构”，右侧有“地图 / 列表”分段切换，“地图”选中；再有一个小筛选器“置信度：全部”。
地图采用三组从左到右的清楚分组，留白均衡。每组顶部是一个业务域标题节点，下面是该域的能力节点；只用短而清楚的细线表达“域包含能力”。不要绘制能力之间的依赖、调用或数据流。
第一组“订单与售后”，包含三个能力：“订单创建”“订单取消”“退款审批”。
第二组“支付与结算”，包含两个能力：“支付确认”“退款执行”。
第三组“用户与会员”，包含两个能力：“用户认证”“会员权益”。
总共必须是三个业务域、七个能力，不增加其他业务层级。
域标题节点背景略深，能力节点是白色小卡片，每张显示能力名和很小的置信度标签。多数为“中置信度”，不要显示百分比。
“退款审批”节点用蓝色边框和浅蓝底突出，附小字“关联变更 5”。
“会员权益”节点附琥珀色小图标和“低置信度”，副注“路径推断”。
在地图底部显示低调图例：“图谱推导”“路径推断 · 低置信度”。底部右侧可放缩小、100%、放大、适配视图的小工具按钮。
整体要像可交互的业务结构地图，节点位置规整，连线不会穿过文字，不画成凌乱的力导向网络，也不是源代码文件树。

【最近变更：地图下方】
面板标题“最近变更”，旁边小字“显示最近 4 条”，右侧文字链接“查看全部”。
面板标题下方有一个默认未勾选的选项“仅看退款审批”，表明当前列表仍显示全项目的最近变更。
采用四行整齐的列表，包含时间、变更摘要、类型、Git 状态。类型与 Git 状态用独立标签。
第一行：今天 09:42 | 新增退款审批 | 变更 | 待提交
第二行：今天 09:15 | 纠正退款影响范围 | 纠正 | 已提交
第三行：昨天 18:20 | 新增会员权益校验 | 变更 | 待提交
第四行：昨天 17:05 | 补充支付确认逻辑 | 变更 | 已提交
第一行整行淡蓝背景，左边短蓝色选中条，表示右侧打开的是它；可以在摘要下显示小字“退款审批 · 3 个文件”。
第二行保留细小历史关联图标与“查看原记录”文字，体现追加纠正的产品特性。
第三行可以有轻量琥珀色点状提示，呼应地图中的低置信度能力。
标签不使用大面积鲜艳色块，不把“已提交”画成“测试通过”。列表底部不要添加销售统计或无关图表。

【右侧变更详情：证据阅读区域】
右侧面板从顶部栏下方延伸到底部，左边一条细分隔线，内部留白 20px。
顶部小标题“变更详情”，右侧关闭图标。
主标题“新增退款审批”，下方并列两个标签“变更”“待提交”。
再显示时间“2026-09-10 09:42”和来源“Codex”。

依次排布以下内容块，标题小而清楚，正文简短可读：
1. “原始需求”：为退款申请增加审批步骤，并保留审批记录。
2. “变更摘要”：新增审批处理逻辑，补充接口与测试文件。
3. “影响能力”：蓝色标签“订单与售后 / 退款审批”。
4. “变更文件 · 3”：用文件图标和等宽字体逐行显示
   src/refund/review.ts，行尾“新增”
   src/refund/routes.ts，行尾“修改”
   tests/refund/review.test.ts，行尾“新增”
   路径过长时可合理缩略，但不能重叠或溢出。
5. “测试证据”：中性灰色状态“未采集”，辅助说明“本次任务没有结构化测试结果”。不能因为存在测试文件而显示测试通过。
6. “能力来源”：显示“图谱推导 · 中置信度”，用辅助小字说明“能力来源于结构分析”。这个置信度属于关联能力，不是整条变更的质量评分。
7. “提交信息”：状态“待提交”，说明“记录尚未包含在 Git 提交中”。不要显示虚构的 commit SHA。

底部有低调的次要按钮“查看原始记录”和“复制记录 ID”。不出现批准、拒绝、立即部署、运行 Agent、提交代码或删除记录按钮。

【质量约束】
最重要的视觉锚点是业务地图、选中的退款审批节点、对应的变更详情。用户一眼能看懂：有哪些能力、发生了什么变化、能用什么证据追溯。
中文标题和状态文字必须清晰、真实、简短，避免随机字符和大段密集小字。保持对齐、行高、边距和图标风格一致，确保右侧内容完全容纳、页面没有遮挡与裁切。
不要生成营销首页、Hero 大横幅、价格套餐、用户评价、收入仪表盘、任务看板、聊天机器人输入框、代码编辑器、3D 地球、霓虹发光网络、玻璃拟态、巨大渐变背景、无意义环形图、完成度评分或装饰性数据曲线。
最终只输出这一张完整的高保真应用界面图。
```

生成后优先检查：3 个域与 7 个能力是否正确；24 条记录是否与 20 已提交、4 待提交一致；选中能力、选中变更和详情是否对应；测试是否显示“未采集”；“纠正”与“已提交”是否是两个独立状态维度。

如果工具不支持指定分辨率，优先保持 8:5 横向比例及三栏结构。图中文字若有误，后续实现时以本提示词为准，不沿用图中乱码或虚构功能。
