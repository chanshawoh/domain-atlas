# DomainAtlas Web UI 产品梳理

日期：2026-09-10。用于首版 Web UI 设计与后续实现；页面能力是本阶段建议范围，不表示已有 Web 服务或前端实现。

## 1. 产品定位

DomainAtlas 是面向 AI 辅助开发的本地业务地图与变更记录工具。

它从第一次开发任务开始，保存用户需求、任务完成摘要、实际观察到的文件变化和证据，将变化关联到“业务域 → 业务能力”，并通过 Git 判断记录是否已被提交。用户可以从业务能力追溯历史，也可以从一条变更找到需求、文件和来源。

一句话介绍：**让每次 AI 开发，都留下可追溯的业务变化。**

产品定位中的业务地图是根据开发证据逐步形成的结构，不保证覆盖项目全部业务；当前能力名称主要来源于包、符号和路径，尚不具备完整的业务语义理解。

## 2. 面向谁，解决什么问题

| 使用者 | 核心问题 | 产品给出的信息 |
| --- | --- | --- |
| 使用 Codex 开发的个人开发者 | 上次为什么修改这里，具体改了什么？ | 原始需求、任务摘要、变更文件、任务来源 |
| 接手项目的开发者、技术负责人 | 当前沉淀了哪些业务能力，最近哪些能力变化了？ | 业务域和能力结构、关联变更、来源与置信度 |
| 需要审阅 AI 修改的人 | 这条记录有何证据，是否已进入 Git 历史？ | 文件版本、显式测试证据、提交状态、提交 SHA |

技术负责人是阅读者角色描述；首版没有账号、角色权限、团队协作或审批流程。

## 3. 已实现能力与验证边界

| 功能 | 当前能力 | 展示时必须保留的边界 |
| --- | --- | --- |
| 任务自动记录 | 接收 Codex 开始/结束事件，开始时保存快照，结束后追加记录 | 2026-09-09 已在真实任务中验收一次自动闭环；不承诺所有宿主和安装环境均已验证 |
| 增量文件识别 | 保存路径、修改前后 blob ID 和模式；覆盖新增、删除、重命名等情况 | 表示本轮期间观察到的变化，不能证明共享 worktree 下的独占作者归属 |
| 业务结构发现 | 根据图谱结构发现域和能力；限制查询范围和预算 | 结构推导不等于人工确认的业务语义，预算不足时可能不完整 |
| 降级处理 | 图谱不可用时按变更路径生成低置信度节点 | 普通 Provider 错误不会静默降级，低置信度必须可见 |
| 证据记录 | 保存需求、文件路径、图谱来源、显式录入的测试结果 | 未采集测试结果不能显示“测试通过”或“测试未运行” |
| 追加式历史 | 保存原始变更，纠正和撤销通过 supersedes 引用已有记录 | 撤销记录不代表工具执行了 git revert；纠正不会直接修改旧事实文件 |
| Git 生命周期 | 推导 pending / committed，并查询首次包含记录的提交 | “已提交”指事实记录进入 Git 历史，不代表已推送、部署或业务验收 |
| 选择性暂存 | CLI 支持预览，完整文件版本匹配时可暂存记录和依赖 | 部分暂存、前置修改、多任务合并不能安全匹配时保留未匹配 |
| 存储可靠性 | .domainatlas JSON 为事实源，原子发布、不覆盖、同轮去重 | Web 查询、索引和缓存都应可重建 |

## 4. 产品对象与关系

- 业务域：一级分组，包含名称、置信度、来源证据。
- 业务能力：归属一个业务域，包含名称、置信度、来源证据。
- 变更记录：包含需求、摘要、时间、任务来源、文件变化、受影响能力、测试证据以及可选历史引用。
- 一条变更可以关联零个、一个或多个能力；同一能力可关联多条变更。纯文档或问答记录可以没有关联能力。
- 文件与证据出现在详情中，不作为第三层业务能力。
- 业务域包含能力、变更影响能力、记录纠正/撤销另一条记录，这三种关系应分别表达；不凭空绘制能力之间的依赖或调用关系。

置信度采用现有 low / medium / high 枚举，对应“低 / 中 / 高”；没有准确率百分比。置信度属于域、能力及其证据，不能作为整条变更的质量分数。

## 5. 首版 Web UI 建议范围

### 核心路径

打开项目 → 查看业务地图 → 选择能力 → 查看关联变更 → 选择变更 → 查看需求、文件、证据与 Git 状态。

也支持从“变更记录”直接搜索一条需求，再追溯受影响能力。首版以当前单个本地 Git 项目为工作范围。

| 页面或区域 | 首版功能 | 需要补齐的查询能力 |
| --- | --- | --- |
| 业务地图（默认页） | 域与能力两级地图、列表切换、名称搜索、置信度筛选、能力选中状态 | 读取域与能力，关联变更数量，保持孤立/低置信度节点可解释 |
| 页面顶部摘要 | 业务域数、能力数、变更数、待提交记录数 | 对当前项目事实进行一致的汇总；数值不代表覆盖率或开发完成度 |
| 最近变更 | 倒序列表、类型和提交状态、影响能力；支持只看选中能力 | 按 recordedAt 排序、稳定次级排序、分页和能力过滤 |
| 变更记录页 | 关键词、日期、类型、Git 状态筛选 | 需求/摘要搜索，change/correction/revert 和 pending/committed 独立筛选 |
| 右侧详情面板 | 需求、摘要、变更文件、测试证据、任务来源、提交信息、历史引用 | 记录详情、能力名称解析、Git 生命周期、supersedes 前后关联 |
| 能力详情 | 所属域、来源与置信度、关联变更 | 域/能力证据与变更的交叉查询；与变更详情复用侧栏空间 |
| 接入说明 | 初始化、构建、钩子启用的静态指引 | 首版可用静态文档；没有健康检测时不显示“实时在线” |

所有 Web 功能尚待实现。先建设统一的只读查询层和本地 API，再接页面；页面不直接拼装磁盘路径读取事实，也不把业务规则散落到前端。

### 展示规则

1. **类型和状态分开**：变更/纠正/撤销是一组；待提交/已提交是另一组。纠正记录也可以待提交。
2. **历史完整**：默认能看到原记录与纠正记录，双向显示关联。首版不宣称已经重算出完整“当前有效业务状态”。
3. **测试证据诚实**：空数组显示“未采集”；显式 not-run 显示“未运行”；passed/failed 显示“通过/失败”，同时可查看命令。测试文件存在不等于执行过测试。
4. **不完整信息可解释**：没有关联能力显示“暂无关联能力”，缺少旧版文件版本显示“该记录未保存文件版本”。
5. **来源清楚**：图谱推导与路径推断分开，低置信度有文字与图标提示，不只依赖颜色。
6. **加载和错误独立**：区分加载中、尚无记录、筛选无结果、事实文件损坏和 Git 读取失败；失败不能显示成零条数据。
7. **图谱不制造噪声**：以域分组能力，控制连线；节点定位表达归属，选中状态表达当前阅读上下文。
8. **读操作为主**：支持筛选、查看、刷新、复制引用。首版不在 Web 中提交代码、删除事实、修改历史或运行 AI 任务。

### 后续能力

Web 内追加纠正、暂存操作、数据库投影、MCP 传输、多任务差异合成、自动测试结果采集、多项目统一管理、业务语义增强、任务缓存清理均不纳入首张界面和首版只读范围。以后按实际需求分别设计。

## 6. 首张界面图的构图

画面：**业务地图工作台，右侧已展开一条变更详情**。这是一张应用内部界面，不是产品官网。

布局为顶部项目栏、左侧导航、中央业务地图与最近变更、右侧详情。把地图和证据放在同一个视野，帮助用户理解“一个能力最近发生了什么，依据是什么”。

首张图使用“Commerce · 商城服务”示例项目，明确标注“示例数据”。业务标签是为视觉稿人工编写的演示文案，不代表当前系统自动生成了这些完整语义。当前项目的真实少量记录另用于后续接真实数据验收。

示例数据固定为 3 个域、7 个能力、24 条记录，其中 20 条已提交、4 条待提交。图中仅展示最近 4 条，不能将最近列表长度误当总数。

推荐浅色桌面工作台：暖灰背景、白色内容面板、深灰文字、少量蓝色选中态。用紧凑的栅格、轻边框和清楚的文字层级建立专业感；不使用装饰性统计图、增长率或虚构健康评分。
